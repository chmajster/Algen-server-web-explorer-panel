# Releasing WebNAS

`VERSION` in the repository root is the single source of truth for the project version. The supported format is strict Semantic Versioning `MAJOR.MINOR.PATCH`.

`scripts/sync-version.py` keeps `pyproject.toml`, `frontend/package.json`, and the root package metadata in `frontend/package-lock.json` synchronized with `VERSION`.

## Verify version metadata

```bash
python scripts/sync-version.py --check
```

The command does not modify files. It exits with a non-zero status when the version is invalid or metadata differs from `VERSION`.

## Bump the version

```bash
python scripts/sync-version.py --bump patch
python scripts/sync-version.py --bump minor
python scripts/sync-version.py --bump major
```

A bump updates `VERSION` and synchronizes the Python and frontend package metadata. It does not create a commit, tag, or push anything.

## Example patch release

Starting from `0.1.21`:

```bash
python scripts/sync-version.py --bump patch
python scripts/sync-version.py --check

git diff
git add VERSION pyproject.toml frontend/package.json frontend/package-lock.json
git commit -m "chore: release v0.1.22"

git tag v0.1.22
git push origin main
git push origin v0.1.22
```

Before tagging, run the normal project checks or ensure the commit passed the protected `main` CI.

## Release workflow

A tag matching `vX.Y.Z` starts `.github/workflows/release.yml` on a GitHub-hosted runner.

The workflow:

```text
vX.Y.Z tag
  -> verify scripts/sync-version.py --check
  -> verify tag version == VERSION
  -> verify tagged commit is reachable from main
  -> backend Ruff / mypy / Bandit / pytest
  -> python -m build
  -> frontend lint / typecheck / Vitest / build
  -> frontend deployment-contract validation
  -> backend distributions + frontend tarball
  -> SHA256SUMS
  -> GitHub Release
```

If `v0.1.22` points at a commit whose `VERSION` is `0.1.21`, the workflow fails before building or publishing a release.

## Release artifacts

The release contains the existing Python distribution generated by `python -m build`, a compressed `frontend/dist` production build, and `SHA256SUMS`. The same files are also uploaded as a GitHub Actions artifact.

## Permissions

Normal CI uses `contents: read`. The release workflow alone requests `contents: write`, because publishing a GitHub Release requires it. No release secret is stored in the repository; the workflow uses the short-lived GitHub token provided to the job.
